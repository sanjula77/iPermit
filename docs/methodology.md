# Methodology

## 1. Overview of the Development Approach

iPermit was built using an incremental, requirement-driven development process rather than a single up-front design-then-build cycle. Fourteen functional requirements (REQ-1 through REQ-14, [requirements.md](requirements.md)) were decomposed into eight sequential implementation phases plus a final evaluation phase ([tasks.md](tasks.md)), with each phase producing a working, independently testable increment of the system rather than a partial layer spanning the whole application. A phase was not considered complete until its code had been exercised against the actual running backend — not only against its own unit and integration test suite — and any discrepancy between the intended design and the verified behaviour was recorded rather than silently corrected in the documentation.

This approach was chosen for three reasons specific to the project's constraints. First, the system integrates two independent AI subsystems (facial recognition and, originally, automated violation detection) whose behaviour cannot be fully specified in advance; committing to a rigid waterfall design risked designing around assumptions that later proved false. Second, the project's own planning documents flagged that prior research behind this thesis had produced an unverified, likely overfit accuracy claim (100% face-match accuracy on a six-person, sixty-eight-image dataset); an incremental approach made it possible to build the recognition pipeline first and defer any accuracy claim until a proper evaluation harness existed, rather than repeating the earlier mistake. Third, working software at each phase gave a concrete artefact to verify claims against, which is treated throughout this project as a precondition for describing anything as "done."

## 2. Requirement Analysis and Design Method

Requirements were captured in EARS-style acceptance criteria ("THE system SHALL...", "WHEN X, THE system SHALL Y", "IF X, THEN THE system SHALL Y") rather than free-form user stories alone, so that each criterion could later be checked off against an observed behaviour instead of a subjective judgement of "looks right." Each requirement in [requirements.md](requirements.md) is traceable forward to the design document's component map and data flows ([design.md](design.md)) and backward from every implementation task in [tasks.md](tasks.md), which cites the requirement(s) it satisfies.

A recurring methodological decision in this project was to treat the source thesis proposal documents as historical context only, not as an authoritative specification. Those documents contained conflicting technology-stack drafts across different chapters and unverified performance claims. Rather than reconciling them retroactively, an Architecture Decision Record was written into [design.md](design.md) explicitly naming the superseded alternatives (Node.js/Express/MongoDB; Flutter/Firebase; DeepFace/Facenet) and the reasoning for the final stack (FastAPI, PostgreSQL, SQLite/FAISS, Expo/React Native, Next.js), so that the discrepancy could be explained as a documented decision rather than an oversight.

Where a requirement had a genuine design ambiguity or a trade-off that materially affected user privacy, correctness, or scope, the decision was not made unilaterally during implementation. Two examples illustrate this: the exact formula and tier thresholds for the driver behaviour badge system (REQ-11) were proposed, discussed, and explicitly approved before any code was written, following a structured brainstorming step; and a conflict between REQ-13 AC5 ("notify nearby drivers of new high-severity incidents") and the project's own privacy non-functional requirement ("incident location is point-in-time only, not continuous tracking of a driver") was surfaced as an explicit choice — implement AC5 by building a live-location subsystem that would violate the stated privacy constraint, or deliberately leave it unimplemented — rather than resolved silently in either direction.

## 3. Tools and Technology Stack

| Layer | Technology | Rationale |
|---|---|---|
| Backend API | FastAPI (Python), SQLAlchemy, Alembic, PostgreSQL | Async-capable, typed request/response models, mature migration tooling for a relational schema with foreign-key integrity constraints (e.g. `ON DELETE RESTRICT` on violation/fine/appeal records) |
| Driver & police mobile app | Expo, React Native, TypeScript | Single codebase across iOS/Android/web preview; Expo's managed workflow removed the need for native build tooling during development |
| Admin web dashboard | Next.js, React, TypeScript | Server-rendered admin UI, shared TypeScript conventions with the mobile app |
| Facial recognition | RetinaFace + ArcFace (ONNX Runtime), FAISS, SQLite | RetinaFace/ArcFace via the `buffalo_l` model pack gave a pretrained detection-plus-embedding pipeline without requiring a from-scratch training dataset; FAISS gives sub-linear nearest-neighbour search over embeddings; SQLite isolates biometric templates from the primary PostgreSQL store, both for the non-functional privacy requirement and to avoid running two ORMs against one schema for a single table |
| Violation detection (planned) | YOLOv8n-seg, YOLOv8n, OpenCV | Selected for the design but not implemented in this build — see §7 |

Every third-party dependency introduced during implementation was justified against an existing requirement rather than added speculatively; no dependency was added purely to make a future, unspecified feature easier to build later.

## 4. Per-Module Implementation and Verification Methodology

The following subsections describe how each major feature was built and verified. Each module was implemented against its own requirement(s), then checked against the live running system (via `docker compose`, a browser preview, or direct API calls) in addition to its automated test suite — the project's working rule is that a test suite passing is necessary but not sufficient evidence of correctness on its own.

### 4.1 Authentication and Role-Based Access Control (REQ-1)

**Method:** JWT-based authentication was implemented first, ahead of every other module, since every subsequent feature depends on knowing which of the three roles (DRIVER, POLICE, ADMIN) is making a request. Passwords are hashed, never stored or logged in plaintext; role is derived server-side from the authenticated user record and cannot be supplied by the client at registration, closing an obvious privilege-escalation path before any other endpoint existed.

**Verification:** registration, login by either email or NIC, rejection of a wrong password, and role-scoped access to a protected route were all exercised directly against the running backend rather than assumed correct from the test suite alone, with seven automated tests covering the same behaviour as a regression baseline.

### 4.2 License Application Submission and Review (REQ-2, REQ-3, REQ-4)

**Method:** The application-submission endpoint enforces an exactly-four-photo rule and structural image validation (content type, decodability) at the point of upload, with any partial upload cleaned up on failure so a rejected submission never leaves orphaned files on disk. Admin review was built as an explicit state machine (`PENDING → APPROVED` or `PENDING → REJECTED`) that rejects any attempt to re-decide an already-decided application. Digital license issuance (license number, QR token, expiry) is committed in the same database transaction as application approval, so the two states can never diverge.

**Verification:** the full submission → review → approval → license-issuance chain was exercised end-to-end in a browser preview against the live backend, not only via automated tests. Two implementation defects were found and fixed during this verification step rather than assumed away: a test-isolation bug in a rate limiter, and an error-message path that silently swallowed a specific exception type.

### 4.3 Facial Recognition Enrollment (REQ-5)

**Method:** The face recognition pipeline (RetinaFace detection → ArcFace embedding, both via ONNX Runtime) was stood up as an independent module before it was wired into the application-approval flow, so its correctness could be verified in isolation first. Enrollment builds one averaged, re-normalised embedding from four submitted photos, requiring every pairwise cosine similarity between the four to clear a configured match threshold — a deliberate mitigation against the overfitting risk flagged in the project's own prior research, since it forces every enrollment photo to plausibly be the same face before that identity enters the system at all. This threshold, and every other quality-related numeric threshold added later, is stored as a named, commented configuration value explicitly marked as an unvalidated starting point rather than a measured constant, so that the eventual evaluation step (§4.7) has a clear, auditable list of what still needs validating against real data.

Two enhancements were made after the initial pipeline was verified working: CLAHE (contrast-limited adaptive histogram equalisation) was added to the detection pipeline to normalise lighting variation prior to detection, and a photo-quality gate (detection confidence, minimum face size, blur via Laplacian variance, brightness range) was moved from running only at admin-approval time to running at submission time, so a driver receives feedback on a poor enrollment photo immediately rather than after an administrator has already reviewed the rest of the application.

**Verification:** enrollment was verified against the running backend with real photographs, not synthetic data only, confirming that a consistent four-photo set produces a searchable, self-matching template, and that an inconsistent or faceless photo is rejected without partially writing a license or an orphaned face template. The quality-gate enhancement was implemented and reviewed using a subagent-driven development process (independent implementation, independent code review, and a final whole-codebase review each treated as separate steps), which surfaced and corrected a defect where a rejected enrollment photo could be left on disk — a bug that had not been caught by any single-task review in isolation, only by the final full-diff review.

### 4.4 Police Roadside Verification (REQ-6)

**Method:** Officer-facing verification supports three independent methods (live face scan, QR-code scan, NIC/license-number lookup) rather than relying on face matching alone, since REQ-6 explicitly requires that an ambiguous or low-confidence face match never be auto-confirmed. Any match below the configured similarity threshold, or a search with no close candidate at all, sets an explicit `requires_manual_confirmation` flag and returns ranked candidates for the officer to choose from rather than silently picking the closest one.

**Verification:** verified live against a real enrolled driver (a genuine match returning similarity 1.0 against the driver's own enrollment photo) and against an empty index (correctly returning no candidates and requiring manual confirmation rather than erroring). Role enforcement was verified by confirming a driver account receives a 403 response from every officer-only route.

### 4.5 Violation Recording, Points, Fines, and Appeals (REQ-7, REQ-8, REQ-9, REQ-10)

**Method:** Automated white-line violation detection (YOLOv8-based lane and vehicle detection with a three-tier overlap check) was designed in [design.md](design.md) but deliberately not implemented in this build. No training dataset or GPU resource was available in the project environment, and the source materials for this thesis do not include a reusable trained model; this was raised explicitly with the project owner rather than silently stubbed out, and the decision taken was to defer Phase 5.4/5.5 and continue with the point-deduction, fine, and appeal workflow using manually recorded violations, leaving the evidence-reference field in place so an automated detector could populate it later without a schema change.

Point deduction, fine generation, and license suspension are committed as one database transaction per violation, so a partial update (points deducted without a corresponding fine, for instance) cannot occur. The per-offense point schedule and fine amounts are explicitly flagged in code as placeholder values not sourced from any real Sri Lankan traffic-fine schedule, following the same honesty convention used for the face-match threshold. Point restoration on payment or a successful appeal reuses one shared function rather than duplicating the restoration rule in two places, since payment and appeal-overturned are mutually exclusive paths out of an unpaid fine and a single shared implementation removes the risk of the two rules drifting apart.

**Verification:** verified live by recording violations against a real driver account through the mobile UI and confirming point accumulation, suspension at the ten-point threshold, and reactivation on payment, in addition to the automated regression suite for this module.

### 4.6 Driver Behaviour Analytics (REQ-11)

**Method:** The badge/tier system is a transparent, rule-based formula over an existing driver's points, unpaid fines, lifetime violation severity, and account tenure, deliberately not a machine-learning classifier, so that a driver or administrator can see exactly why a given tier was assigned rather than treating it as an opaque prediction. Because this formula and its tier thresholds directly affect how a driver is characterised to an administrator, the design was proposed in chat, discussed, and explicitly approved before implementation began, rather than decided unilaterally during coding. The formula was implemented as a pure function with no I/O, which made it independently testable against eighteen synthetic input cases covering boundary conditions at each tier threshold, separately from the integration path that recomputes a badge after any state-changing event (approval, violation, payment, appeal resolution).

**Verification:** verified live that a newly approved driver receives an initial PLATINUM badge, that a severe violation forces a SUSPENDED badge even when the underlying numeric score alone would map to a higher tier (the license-status override takes precedence over the score), and that paying off a fine restores most, but not all, of the score — a small permanent deduction remains by design, since violation history is immutable once recorded.

### 4.7 Notifications and Road Incident Reporting (REQ-12, REQ-13)

**Method:** In-app notifications were modelled as a flat, pre-rendered message string per event rather than a generic structured payload, a deliberate simplification given the project's scope, and wired as a best-effort step after each triggering flow's own database commit rather than inside the same transaction, since a failed notification should never roll back a successful license approval or payment. Push delivery via Expo's push API follows the same best-effort principle. Road incident "nearby" search uses a Haversine distance calculation in Python rather than a dedicated geospatial database extension, judged proportionate to the scale of this project. Incident expiry is checked lazily whenever incidents are read, rather than via a background scheduler, since no scheduled-job infrastructure exists elsewhere in the system.

One acceptance criterion, REQ-13 AC5 ("notify nearby drivers of new high-severity incidents"), was identified during design as being in direct tension with the project's own privacy non-functional requirement, which limits incident location data to a point-in-time report rather than continuous tracking of a driver's position — proactively notifying "nearby" drivers of a new incident requires knowing where those drivers currently are. This conflict was raised explicitly rather than resolved by implementing one requirement at the expense of the other silently; the decision taken was to implement AC1 through AC4 in full and leave AC5 unimplemented, documenting the conflict as the reason rather than recording it as an oversight.

**Verification:** verified live that a location-permission denial falls back to a default coordinate rather than failing the screen entirely, and that reporting, confirming, and clearing an incident all update the nearby list correctly. Two verification gaps are recorded rather than hidden: push notification delivery itself was not confirmed against a physical device, since none was reachable from the development environment, only the request-construction and error-handling logic; and the native map rendering component was built to the mapping library's documented interface but not visually confirmed, since the only available test surface (a browser preview) does not render that native component.

## 5. Testing Strategy

Three layers of testing were applied across every module: unit tests for pure business-rule functions with no I/O (point deduction, badge-tier thresholds, appeal-reversal logic, face-recognition quality assessment, and the FAR/FRR/EER evaluation formulas), integration tests exercising each phase's endpoints against a real test database, and a final round of live verification against the actual running Docker stack for every phase, since a passing automated suite was treated throughout this project as necessary evidence, not sufficient evidence, of a working feature. Where a defect was found only through live verification and not through the existing automated tests, a new regression test was added alongside the fix rather than relying on manual verification alone to catch a recurrence.

For the two AI subsystems, an additional evaluation layer is planned specifically to avoid repeating a known methodological error from the source research: a prior attempt at face recognition reported 100% training accuracy but only 60% test accuracy on a six-person, sixty-eight-image dataset, a textbook overfitting result. A FAR/FRR/EER evaluation harness (pure functions for computing false-acceptance and false-rejection rates across a threshold sweep, plus a command-line tool for running it against a directory of labelled photographs) has been built and unit-tested against synthetic score distributions, but has not yet been run against a real evaluation dataset, since no properly sized, held-out dataset currently exists for this project. This is treated as an explicit open decision for the project owner — among sourcing a public face-verification dataset, collecting real enrollment data over time with consent, or constructing a small purpose-built dataset — rather than a gap to be quietly closed with an unrepresentative sample.

## 6. Verification Discipline and Documentation Practice

Two practices were applied consistently across all eight phases and are worth stating explicitly as part of the methodology, since they shape how the results in this report should be read.

First, every numeric threshold introduced without a measured basis — the face-match similarity threshold, the CLAHE-based quality-gate thresholds, the point-deduction schedule, the fine amounts, the incident-expiry window — is recorded in code with an explicit comment stating that it is an unvalidated starting point, not a measured constant. This convention exists specifically because the project's own prior research contained a performance claim that did not hold up once tested rigorously, and the intent is that no equivalent claim in this report can be mistaken for a validated result.

Second, when a phase's implementation deviated from its original design, or a requirement's acceptance criterion could not be fully satisfied for a documented reason (deferred violation detection, the REQ-13 AC5 privacy conflict, unverified push delivery, unverified native map rendering), that deviation is recorded in [tasks.md](tasks.md) alongside the completed work rather than omitted from it. This report's account of what was built is drawn from that record, not reconstructed after the fact.

## 7. Limitations of the Adopted Methodology

The incremental, single-developer approach adopted here has trade-offs that should be acknowledged directly. Automated violation detection (REQ-7), the second AI subsystem in the original design, remains unimplemented; the point/fine/appeal workflow was built and verified against manually recorded violations instead, and this substitution should be read as a deliberate, documented scope decision rather than an incidental gap. The face-recognition and violation-detection accuracy figures cited in the source research (100% face-match accuracy on six people; approximately 85% mAP50 for lane detection) are prior work's results on a different dataset, not this system's own measured performance, and are not repeated as claims about this system anywhere in this report. Finally, several verification steps (push notification delivery to a physical device, native map rendering, and any load or concurrency behaviour under multiple simultaneous users) were constrained by the tooling available during development rather than by design, and are named here as boundaries of what has actually been confirmed, not as claims that these paths are known to work correctly.
